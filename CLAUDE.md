# Transly — інструкція для Claude Code

Мова спілкування з власником: **українська**. Відповідай коротко й по суті. Власник не програміст: пояснюй простими словами, без зайвого жаргону.

## Що це
Робоче місце перекладача ігор (RPG Maker та ін.) на українську. Поточна версія: TypeScript-інтерфейс у Tauri (`app/`), лише **ПК/Windows**. Телефон (`app/src/mobile`) і браузерна версія **не підтримуються й не збираються**.
Іде переписування на **Rust з нативним інтерфейсом без вебвʼю** (причина: WebView2 бере ≈745 МБ пам'яті на проєкті з 105 тис. рядків). План: `/root/.claude/plans/…` не в репозиторії, тому коротко тут:
0. Прототипи (`rust/proto-egui`, `rust/proto-slint`, порівняння в `rust/PROTO-COMPARISON.md`) — зроблено; рекомендовано **egui**.
1. `transly-core` у `rust/`: переклад `app/src/core/*.ts` у Rust. Еталон — наявні тести (1500+): експортувати «золоті вектори» (входи/виходи JSON) з vitest і звіряти в `cargo test` до побайтної рівності.
2. Платформа (`app/src-tauri/src/lib.rs`, ≈1,3 тис. рядків) → Rust-крейт.
3. Інтерфейс на egui по екранах, потім тести інтерфейсу, паритет, випуск.
Формат збереженого проєкту (`project.json`) **не змінюється**. Старий застосунок (`app/`) живе й випускається, доки новий не досягне паритету.

## Команди (Windows, PowerShell; теку краще тримати поза OneDrive)
Веб/Tauri-частина (`cd app`):
```
npm ci
npm run typecheck        # tsc --noEmit
npm test                 # юніт-тести (vitest), ≈1500
npm run test:ui          # браузерні сценарії Playwright (усі; довго)
npm run build            # тип-перевірка + збірка
npm run tauri build      # інсталятор Windows
```
Rust-частина (`cd rust`): `cargo check`, `cargo test`, `cargo clippy -- -D warnings`, `cargo build --release -p proto-egui`.
Окремий сценарій інтерфейсу: зібрати `npx vite build --outDir <тека>`, `npx vite preview --outDir <тека> --port 4301 --strictPort`, потім `PC_URL=http://localhost:4301/ node test-ui/<файл>.cjs`.

## Правила, які не обговорюються (не перепитуй)
1. **Перед кожним комітом**: `typecheck` + `npm test` (і `cargo test`, якщо торкався `rust/`). Не послаблюй і не пропускай тести та CI, щоб «позеленіти»; якщо тест падає — знайди причину.
2. **Випуск ПК**: GitHub → Actions → «Desktop app» з `release: true` (через `gh workflow run desktop.yml --ref ccr-a0ee6fc6-t2at3x -f release=true`). Після збірки перевір, що реліз `desktop-latest` має `target_commitish` = поточний HEAD. Збирається ≈5 хв. Android **не** випускати. Випуск роби, коли власник просить («запусти збірку»).
3. **Видимі зміни інтерфейсу**: спершу мокап на реальному DOM/зображенні, власник обирає, потім код. Дрібні виправлення за скріншотом власника — одразу.
4. Дизайн: єдина система станів і акценту (`app/src/ui/states.css`, `theme.css`); кнопки S/M/L; **жодних жорстко прописаних hex-кольорів** поза токенами (тест `theme-css` це перевіряє). Колір акценту береться з теми проєкту.
5. Усі зміни рядків перекладу йдуть через «план змін» (`core/plan.ts`, `ctx.commit`) з можливістю «Скасувати»; вичитані рядки масові інструменти **пропускають**. Не пиши в `saved.files` напряму.
6. Дані: ніколи не втрачай переклади. Запис — двофазний, злиття записів комутативне (див. `core/merge.ts`, тести законів злиття).
7. Не змінюй файли гри, лише читай їх (збірка пише в окрему теку).

## Коли питати, а коли ні
**Не питай** про: назви, структуру файлів, вибір бібліотеки в межах схваленого плану, чи писати тести (так), чи коммітити/пушити (так), формулювання повідомлень, дрібні візуальні рішення в межах існуючої системи, чи продовжувати наступний очевидний крок. Приймай розумне рішення й повідом одним реченням, що обрав.
**Питай (коротко, з варіантами й рекомендацією)** лише коли: потрібне рішення, яке змінює напрямок продукту; щось необоротне або назовні (видалення релізів/гілок/даних, публікація, платні сервіси); дві реальні альтернативи з різною ціною для власника; невідомий симптом скарги (що саме не працює).
